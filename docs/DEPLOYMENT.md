# Deployment and operations

There are three ways to run YalaInsight:

1. **Render (recommended):** a managed web service, PostgreSQL + PostGIS and Redis, set up from
   `render.yaml`.
2. **Any Docker host:** `docker compose up -d --build` (PostGIS, Redis, release step, API).
3. **Local development:** see the end of this document.

## 1. Deploy on Render

### What the blueprint creates

`render.yaml` defines three resources in the Frankfurt region, the closest Render region to most
African markets:

| Resource | Purpose | Starting plan |
|---|---|---|
| `yalainsight` web service (Docker) | API, web UI, background scheduler | `starter` |
| `yalainsight-db` PostgreSQL 16 | All data. The PostGIS extension is created by the first migration. | `basic-256mb` |
| `yalainsight-cache` Key Value (Redis) | Shared rate limits across instances | `starter` |

> **Check plans and prices when you import.** The blueprint was written without access to Render's
> live docs. Plan names and prices change; Render shows the effective plan and cost before you
> confirm. Size the database to your data volume: one year of hourly data for a plant with 20
> inverters is roughly 200k rows.

### Steps

1. Merge the pull request into `main`, or deploy the branch directly.
2. In Render, choose **New → Blueprint**, connect GitHub and select `wemuve/YalaInsight`.
3. Render asks for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `YALA_BOOTSTRAP_ADMIN_EMAIL` | Your email (first platform administrator) |
   | `YALA_BOOTSTRAP_ADMIN_PASSWORD` | A temporary password: ≥ 10 characters, letters and digits. You must change it at first sign-in. |
   | `NREL_API_KEY` | Optional (PVWatts baselines). Leave empty if unused. |

   `YALA_JWT_SECRET` and `YALA_DATA_KEY` are generated by Render. **Never change `YALA_DATA_KEY`
   afterwards.** It encrypts 2FA secrets, and rotating it disables every user's 2FA.

4. Click **Apply**. Each time the app starts, `deploy/start.sh` brings the database schema up to date
   and runs the idempotent bootstrap before serving traffic. A database lock means only one
   instance migrates at a time. This works on every Render plan; no pre-deploy hook is needed.
5. Open `https://<service>.onrender.com`. Sign in with the bootstrap email and password, choose a new
   password, then set up two-factor under **My account**.
6. Delete `YALA_BOOTSTRAP_ADMIN_PASSWORD` in the Render dashboard after the first sign-in. The
   bootstrap does nothing once that user exists.
7. Add your domain under **Settings → Custom Domains**. Render issues the TLS certificate.
8. Customers can now create their own account from **Create an account** on the sign-in page. Each
   sign-up gets its own organisation, separate from all others, and its creator becomes that
   organisation's administrator. You can also create organisations yourself under
   **Settings & integrations → Platform**.

> **Can't sign in?**
> - **No account yet:** use **Create an account** on the sign-in page.
> - **Platform administrator account:** this exists only if `YALA_BOOTSTRAP_ADMIN_EMAIL` and
>   `YALA_BOOTSTRAP_ADMIN_PASSWORD` were set before a deploy. If they weren't, set them in Render and
>   redeploy.
> - **Demo passwords** work only on a demo instance (`YALA_LOAD_DEMO=true`).
> - **After 5 wrong passwords** the account is locked for 15 minutes.
>
> **Deploy log says `release: waiting for database…` with `127.0.0.1:5432` / `localhost`, or "No database
> is configured"?** The web service has no database connection string. This happens when the service
> is created with **New → Web Service** instead of the Blueprint. Fix it either way:
> - **Recommended:** delete that service and use **New → Blueprint**. It creates the database, Redis,
>   secrets and settings for you.
> - **Or connect it by hand:**
>   1. Create **New → PostgreSQL** in the same region.
>   2. Copy its **Internal Database URL**.
>   3. In the web service's **Environment**, add:
>      - `YALA_DATABASE_URL` set to that URL;
>      - `YALA_ENV=production`;
>      - `YALA_JWT_SECRET` and `YALA_DATA_KEY`, each a 64-character random value (click **Generate**);
>      - `YALA_SCHEDULER_ENABLED=true`.
>   4. Click **Save, rebuild and deploy**.
>
> **"Internal server error" or "The database has not been set up yet"?** The database schema is
> missing or the app cannot reach the database.
> 1. Open the service's **Logs** in Render and look for lines starting with `release:`.
>    - `release: database is up to date` means the schema is fine. Use the error's reference code
>      to find the failing request in the logs.
>    - `release: FAILED …` names the problem, such as a wrong `YALA_DATABASE_URL` or the database
>      being unreachable.
> 2. Then choose **Manual Deploy → Deploy latest commit**.
> 3. Check `/ready`. It should show `"status": "ready"` and `"db_revision"`.

### Demo instance (optional)

To get a separate demo deployment with the synthetic portfolio, set both variables below to `true`
on a **separate** Render service:

- `YALA_LOAD_DEMO`
- `YALA_SHOW_DEMO_LOGIN`

Demo users share a published password. Never enable this on an instance that holds customer data.

### Tenant-isolation safety check

On start-up in production, the app refuses to run if its database role is a superuser or has
`BYPASSRLS`, because PostgreSQL row-level security would then be silently bypassed. `/ready` reports
`tenant_isolation_enforced`.

Render's database user owns its database but is not a superuser, so the check passes. If you point
the app at another database, create a dedicated role as in `deploy/initdb/01-app-role.sh`.

## 2. Any Docker host

```bash
cp .env.example .env    # fill every value (openssl rand -hex 32 for secrets)
docker compose up -d --build   # db → redis → migrate (release.sh) → api on 127.0.0.1:8000
```

- Put `deploy/Caddyfile` (or nginx) in front for TLS.
- `deploy/initdb/01-app-role.sh` creates the non-superuser `yala_app` role.
- Run `deploy/backup/pg_backup.sh` nightly (see below).

> The Docker build and Compose stack were written in an environment without a Docker daemon and have
> not been executed. The app, migrations and release script themselves are tested.

## Configuration reference

| Variable | Default | Notes |
|---|---|---|
| `YALA_ENV` | `development` | Set to `production` to require strong secrets, enable HSTS and enforce the role check. |
| `YALA_DATABASE_URL` (or `DATABASE_URL`) | local dev DB | Required in production and on Render; start-up stops with instructions if missing. `postgres://`, `postgresql://` and `postgresql+psycopg://` URLs are all accepted. |
| `YALA_JWT_SECRET` | dev value | ≥ 32 characters in production. Changing it signs everyone out. |
| `YALA_DATA_KEY` | — | ≥ 32 characters in production. Encrypts 2FA secrets. Do not rotate. |
| `YALA_REDIS_URL` | — | Shared rate limiting. Without it, limits are per instance. Fails open if Redis is down. |
| `YALA_SCHEDULER_ENABLED` | `false` | Background jobs: webhook retries every minute, anomaly detection on an interval. Safe with many instances (advisory locks). |
| `YALA_DETECTION_INTERVAL_MINUTES` | `60` | How often detection re-runs over the last 3 days of each operational plant. |
| `YALA_JWT_TTL_MINUTES` | `480` | Session length. |
| `YALA_LOGIN_MAX_FAILURES` / `YALA_LOCKOUT_MINUTES` | `5` / `15` | Account lockout. |
| `YALA_RATE_LIMIT_PER_MINUTE` / `YALA_LOGIN_RATE_LIMIT` | `600` / `10` | Per user, and per IP for login. |
| `YALA_MAX_UPLOAD_MB` | `25` | CSV upload limit. |
| `YALA_MAP_TILE_URL` / `YALA_MAP_TILE_ATTRIBUTION` | OpenStreetMap | **Use a commercial tile provider in production.** OSM's public tiles are not for heavy commercial use. The CSP allows the configured host automatically. |
| `YALA_CORS_ORIGINS` | — | Only if another origin calls the API from a browser. |
| `YALA_BOOTSTRAP_ADMIN_EMAIL` / `_PASSWORD` | — | First platform administrator. |
| `YALA_ALLOW_SIGNUP` | `true` | Shows "Create an account" on the sign-in page. Anyone can create a new organisation and becomes its administrator. Set to `false` for invitation-only instances. |
| `YALA_SIGNUP_PLAN` | `enterprise` | Plan given to self-service organisations. Lower it (e.g. `starter`) once paid plans are in place; platform admins can change any organisation's plan. |
| `YALA_SIGNUPS_PER_HOUR` | `5` | Sign-ups allowed per IP address per hour. |
| `YALA_LOAD_DEMO` / `YALA_SHOW_DEMO_LOGIN` | `false` | Demo instances only. |
| `NREL_API_KEY` | — | PVWatts adapter. |
| `PORT`, `WEB_CONCURRENCY` | `8000`, `2` | Set by the host. |

## Operations

**Health checks**

- `/health` is the liveness check.
- `/ready` checks the DB, the migration revision, PostGIS, RLS enforcement, the rate limiter backend
  and the scheduler.

**Metrics.** `/metrics` exposes counters in Prometheus text format. Restrict it at the proxy, or
scrape it from a private network.

**Logs.** JSON on stdout, with `request_id`. On Render, add a log stream (Datadog, Better Stack, …).
Alert on:

- the 5xx rate;
- `/ready` failures;
- `job failed`;
- `webhook delivery failed`;
- `auth.login_locked` spikes.

**Background jobs.** Platform admins see each job's last run and status under
**Settings → Platform → Background jobs**. To run one by hand:
`python -m app.jobs anomaly_detection` (Render Shell).

**Migrations.** Migrations run automatically at start-up via `deploy/start.sh`, or by hand with
`python -m app.release`. Every migration is reversible: `alembic downgrade -1`.

## Backups and recovery

**Backups**

- **Render:** daily backups and point-in-time recovery are included on paid PostgreSQL plans. Check
  the retention for your plan. Add an off-site logical dump weekly, using `deploy/backup/pg_backup.sh`
  from a cron job or a scheduled GitHub Action.
- **Self-hosted:** WAL archiving (pgBackRest / wal-g) to encrypted object storage, plus the nightly
  `pg_backup.sh` dump (GPG-encrypted, 14-day retention).

**Targets:** RPO ≤ 5 min with PITR, RTO ≤ 2 h.

**Restore procedure (test it quarterly on a staging copy)**

1. Restore with Render PITR into a new database, or run `pg_restore --no-owner -d <db> <dump>` into a
   new PostGIS 16 instance, owned by a non-superuser role.
2. Point `YALA_DATABASE_URL` at it and deploy. The release step runs `alembic upgrade head`.
3. Confirm that `/ready` shows `tenant_isolation_enforced: true`.
4. Spot-check one tenant's dashboard.
5. Record the incident.

## 3. Local development

```bash
sudo -u postgres psql -c "CREATE ROLE yala LOGIN PASSWORD 'yala' NOSUPERUSER;"
sudo -u postgres psql -c "CREATE DATABASE yalainsight OWNER yala;"
sudo -u postgres psql -d yalainsight -c "CREATE EXTENSION postgis;"
# same for yalainsight_test (used by the test suite)

cd backend
pip install -r requirements-dev.txt
alembic upgrade head
python -m app.seed --reset
YALA_SHOW_DEMO_LOGIN=true uvicorn app.main:app --reload    # http://localhost:8000
python -m pytest -q
```

**Demo logins.** All demo users share the password `Demo-Password-2026`:

- `admin@demo.yalainsight.local`
- `owner@…`, `analyst@…`, `tech@…`, `viewer@…`
- `admin@other.yalainsight.local` (second tenant)

The platform administrator is `platform@yalainsight.local` with password `Platform-Admin-2026`.
